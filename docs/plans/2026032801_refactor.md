# Refactor: Step Types, Naming, Assertions, and Thread ID Management

## Summary

This refactor covers six areas:

1. **Step type renames**: `user` → `message`, `agui:connect` → `resume`
2. **"Turn" → "Step"** naming throughout the codebase
3. **Client method renames**: `sendMessage` → `message`/`resume` (matching step types)
4. **Thread ID**: moved from target config to context variables (`THREAD_ID`)
5. **`assert` → `expect`**: YAML key and all related types/functions
6. **Assertions simplified**: removed target-level and test-level assertions, deleted merge logic

---

## 1. Step Type Renames

### 1.1 `type: user` → `type: message`

```yaml
# Before
- user: "Hello"

# After
- message: "Hello"
```

### 1.2 `type: agui:connect` → `type: resume`

```yaml
# Before
- type: agui:connect

# After
- type: resume
  resume: "th_existing_thread_id"
```

`resume` field is required (string, the thread ID to resume).

**Behavior:**

- Sets `variables.THREAD_ID` to the provided value
- Destroys existing client
- Creates new client with the thread ID from variables

### 1.3 `type: script` — no change

## 3. Client Method Renames

| Before                              | After                                 |
| ----------------------------------- | ------------------------------------- |
| `ProtocolClient.sendMessage()`      | Removed                               |
| `ProtocolClient.run(options)`       | `ProtocolClient.message(text)`        |
| `ProtocolClient.connect()`          | `ProtocolClient.resume()`             |
| `SendMessageOptions` / `RunOptions` | Removed (simple `text: string` param) |

Client methods now mirror step types: `message()` and `resume()`.

---

## 4. Thread ID: Config → Context Variables

Thread ID is no longer a target config field. It flows through the `Variables` map as `THREAD_ID`.

- Removed `threadId` from `AGUITargetSchema` and `AGUIWSSTargetSchema`
- Runner auto-generates `THREAD_ID` on first message step if not set
- Resume step sets `variables.THREAD_ID` from `step.resume`
- Scripts can set/override via `{ "variables": { "THREAD_ID": "..." } }`
- `createClient` reads `threadId` from `CreateClientOptions` (sourced from variables by the runner)

---

## 6. Assertions Simplified

**Removed target-level assertions:**

- Target config no longer has an `expect` field
- `ConfigExpectBlockSchema` / `ConfigExpectBlock` deleted

**Removed test-level assertions:**

- `TestFileSchema` no longer has an `expect` field
- `evaluateTestAssertions` deleted
- Top-level `expect:` removed from all example YAML files

**Deleted merge logic:**

- `src/runner/merge.ts` and `src/runner/merge.test.ts` deleted
- `mergeExpectBlocks` function removed
- Assertions now live only on steps — no inheritance, no merging
